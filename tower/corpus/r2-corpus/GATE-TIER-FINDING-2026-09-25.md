# The corpus gate measures L6 (retiring); its 9 known-MISCOMPs are ALL fixed in SEM0 (the telos)

Opening the "presult struct-payload pipeline" (one of the 9 gate-tracked MISCOMPs in baseline.txt) surfaced a
structural fact about the gate, not a struct bug.

## What the gate measures
corpus-gate.sh copies `$SP/L6.rzrs` to rzrs.self and runs map.sh with NO marker -> the enforced baseline.txt
(895 OK / 9 MISCOMP) is the **L6 transpiler** board. L6 is the RETIRING tier (dev target is SEM0 = s1_parser.rs).

## The 9 known-MISCOMP are L6-only; SEM0 resolves ALL of them
Measured each of the 9 under the real SEM0 binary ($SP/sem0.frozen, //@S9) with the CORRECT chain
(i64 ld twin $SP/ld.bin | C opt | C ra | cf.hoist):
  grow2_iflet_chain, grow3_match_guard, grow6_shortcircuit_17, grow8_cmp_chain_i64_20, match_guard_multiarm_ast,
  presult_err_struct_scalar_payload, presult_err_struct_string_payload, presult_ok_and_err_struct_payloads,
  presult_ok_struct_multifield_both_arms  -> **all 9 OK under SEM0**.

## The presult root cause (why it fails on L6 only)
Isolated: `fn p(n: i64) -> ... if n < 0` MISCOMPILES on L6 because an **i64 parameter is not sign-extended** at
the call boundary. L6 passes a negative literal as i32 (`v3: i32 = sub ...; v4 = call p v3`), and p holds it as
`i32 = param`; the `lt8 v0 v3` then reads 0x00000000FFFFFFFF (positive) -> takes the wrong arm -> `Ok(-1)`.
Contrast: an i64 LOCAL gets `convs` (sign-extend) on materialization (c2 OK), and an i32 param is fine (c3 OK).
SEM0 sign-extends i64 params correctly (c1 OK under SEM0). So the struct payload was a red herring; the trigger
is i64-param sign-extension, present only on the retiring L6 tier.

## baseline-sem0.txt is INVALID (not just stale)
baseline-sem0.txt (551 MISCOMP) was generated by map.sh's default chain, which uses the C ld
($CC/link/rzir-ld.bin). The C ld clamps heaptop at INT32_MAX and CANNOT link SEM0's 4GB-arena output
(`gdef __heap 4199481344`), so every SEM0 elf segvs -> mass false MISCOMP. A real SEM0 board needs the i64 ld
twin. Do not trust baseline-sem0.txt.

## Recommendation (keeper decision)
Migrate the corpus gate to measure SEM0 (RZ_CC=sem0.frozen, RZ_MARK=//@S9, i64-ld chain3) and regenerate the
baseline from that. This measures the telos tier, flips these 9 to OK, and guards SEM0 regressions going forward
-- the "govern the resolver mechanically" move. Prereq: a CORRECTED full SEM0 board (running) must be >= L6's
895 OK with no SEM0-only regressions L6 handled. Fixing L6's i64-param sign bug is possible but low value (a
retiring tier). See sem0board.txt for the corrected board result.

### The 13 UNSOUND are SEM0 scope, not new codegen bugs
They are deliberately-INVALID probes rustc rejects (borrow_double_mut, consts_unsound_oob, convert_bad_charcast,
ctrlflow_qmark_type_mismatch, ctrlflow_unsound_missing_arm, ints_overflow_add, operators_bad_noimpl,
patterns_or_mismatch, recurse_undefined_call, slices_oob, typeck_field_miss, typeck_method_miss,
typeck_struct_mismatch). L6 rejected them (REJECT-OK); SEM0 compiles+runs them because it is a CODEGEN tier, not
a type/borrow checker -- over-acceptance is SEM0's known scope (owned conceptually by D0, though D0 uses its own
reject-* fixtures, not these). Recorded as baselined UNSOUND (tolerated debt); the ratchet still fails on any NEW
OK->UNSOUND, so the regression guard is intact. Closing them is a front-end-rejection effort, separate from
codegen correctness -- not required for the meta-telos (compile rustc's OWN, already-valid source).
